# Web サイトのレビュー

## 受け付ける形式

- 公開 URL
- ステージング URL（Basic 認証がある場合は、認証情報をアクセス手順に含める）
- ローカルで配信中の URL（`http://localhost:...`）

同じ体験を再現するために、同梱の Playwright MCP を使います。`--isolated` で起動しているため、ログイン状態や Cookie は持ち込まれません。

## 準備手順

1. 到達確認：`curl -sI <URL>` でステータスを確認する。リダイレクト先が意図したページか見る。
2. 表示環境を決める。作者が主にスマホ閲覧を想定しているなら、アクセス手順で「スマホの画面幅で開く」と指示する（Playwright MCP の `browser_resize` を使うよう書く）。
3. 入力・購入・問い合わせ送信など、他者に影響する操作は禁止する。フォームの入力体験が必要なら、送信直前まで、と手順に書く。
4. 開始地点はトップページか、作者が想定する流入ページ（検索結果からの着地ページ、広告のリンク先）。流入ページの指定は「体験の順序の誘導」には当たらないので指定してよい。

## ペルソナに渡すアクセス手順（雛形）

```
1. ブラウザで次の URL を開いてください：<URL>
   <スマホ想定なら：画面幅 390px に変更してから見てください>
2. 普段 Web サイトを見るときと同じように、自由に見てください。
3. フォームの送信、購入、問い合わせ、アカウント作成はしないでください（入力画面まで進むのは可）。
4. ページを移動した順と、各ページで感じたことを記録してください。
```

## 専門家の既定プロファイル

| 既定 | 代替 |
| --- | --- |
| Web ディレクター（LP とコーポレートサイトの制作・改善を10年） | フロントエンドエンジニア（表示速度、レスポンシブ、アクセシビリティ）、SEO 担当者、EC 運営者 |

### 専門家への具体的な問い

1. ファーストビュー（スクロールせずに見える範囲）だけで、何のサイトで、誰向けで、何ができるかがわかるか。
2. 主要な導線（ボタン、ナビゲーション）はどれで、どのページから何クリックで目的のページに着くか。
3. スマホ幅で崩れる箇所、文字が小さすぎる箇所、タップしにくい箇所はどこか。
4. 読み込みが遅いと感じたページ、画像の表示が遅れた箇所はあるか。
5. リンク切れ、404、意図しないリダイレクトはあったか。
6. 信頼感を損なう要素（古い日付、実績の不明確さ、連絡先の欠如、誤字）はあるか。
7. 利用者に通じなさそうな用語・略語はどれか。

## 関心層・無垢・受信者の知識状態のヒント

- 関心層：そのサイトの題材（製品カテゴリ、業界）に興味がある。業界用語は「知らないこと」に。
- 無垢：サイト上の製品名・機能名・略語・業界用語を列挙する。Web の基本操作は知っている。
- 受信者：流入経路（検索語、広告、紹介）と、その時の状況（比較検討中、急いでいる、ただ眺めている）を書く。ただし「申し込もうとしている」のような行動は書かない。

## 判定の観点（シンセサイザーに渡す）

- 各ペルソナはファーストビューで「何のサイトか」を正しく言えたか
- 想定受信者は、作者が期待する行動（非公開情報）の直前（フォーム、申込ページ、問い合わせ）まで自力で到達したか。到達しなかった場合、どのページで止まったか、戻ったか
- 第一印象の信頼感と、熟慮後の評価は一致したか
- 専門家の挙げた表示崩れやリンク切れは、受信者の体験ログにも現れたか

## 実行上の注意

ブラウザはセッションに1つです。ペルソナは**1体ずつ順番に**起動し、各ペルソナの完了後に `browser_close` を呼んでから次を起動します（並列にすると互いのタブと画面状態を共有し、遮断が破れます）。

## 必要なツール

- 同梱の Playwright MCP（閲覧、スクリーンショット、画面幅変更。任意コード実行、ファイル送出、任意 HTTP リクエストはペルソナに与えていません）
- 初回はブラウザ本体の導入が必要です（README 参照）
