# 記事のレビュー

## 受け付ける形式

- Markdown、テキスト、HTML のファイル
- 公開 URL（ログインが必要なページは、作者に本文のコピーを `work/article.md` として用意してもらう）
- Google ドキュメントなどコネクタ経由の文書は、環境のコネクタで本文を取得して `work/article.md` に保存する（コネクタは同梱しない）

## 準備手順

1. ファイルなら文字数を把握し、`work/` へのコピーは不要。URL なら到達確認を行う（ブラウザで開ける、ペイウォールやログインがない）。
2. 公開 URL の場合、ペルソナにはレイアウトや画像込みで体験させたいので、**URL をそのまま**渡し、同梱の Playwright MCP で閲覧させる。原稿ファイルの場合は Read で読ませる。
3. 記事中にリンクがある場合、リンク先まで追うかはペルソナの自由にする（手順で禁止も推奨もしない）。

## ペルソナに渡すアクセス手順（雛形）

ファイルの場合：

```
1. 次のファイルを開いて読んでください：<絶対パス>
2. 普段、記事を読むときと同じように読んでください。全部読む必要はありません。
```

URL の場合：

```
1. ブラウザで次の URL を開いてください：<URL>
2. 普段、記事を読むときと同じように読んでください。全部読む必要はありません。
3. ページ上で入力・投稿・購入はしないでください。
```

## 専門家の既定プロファイル

| 既定 | 代替 |
| --- | --- |
| 商業メディアで記事編集を10年担当した編集者。加えて、記事の題材分野の実務家（題材の表層から職能を具体化する。例：健康分野なら理学療法士、技術記事なら該当技術の上級エンジニア） | コピーライター、SEO 担当者、校閲者 |

題材分野の専門家は、既定の編集者と**別の専門家ペルソナ**として追加してもよい（`--count` ではなく `--personas` で追加）。

### 専門家への具体的な問い

1. タイトルと冒頭が読者にした「約束」は何か。本文はその約束を果たしているか。
2. 冒頭3段落で、読者が読み続ける理由は提示されているか。
3. 主張と根拠は対応しているか。根拠のない断定、出典のない数字、誤った事実はどれか。
4. 削っても意味が変わらない段落・文はどれか。
5. 結びは、読者が次に取る行動や考えを明確にしているか。
6. 読者に通じないおそれのある用語・略語はどれか。
7. 題材分野の専門家として、誤り・古い情報・誤解を招く表現はどれか。

## 関心層・無垢・受信者の知識状態のヒント

- 関心層：題材に興味があり、入門的な知識はある。記事の見出しに出てくる専門語から「知らないこと」を3〜6個拾う。
- 無垢：題材の語彙を全体から拾って列挙する。固有名詞（製品名、サービス名）も知らない。
- 受信者：記事に出会う場面（SNS、検索、メール、社内共有）を状況に書く。読む端末と時間の余裕を具体的に。

## 判定の観点（シンセサイザーに渡す）

- 各ペルソナはどこまで読んだか。離脱した位置と理由は、受信者の離脱点と一致するか
- 「一番言いたいこと」として受け取られた一文は、作者の意図と一致したか
- 想定受信者が読了後に取ると答えた行動は、期待する行動と一致したか。一致しない場合、何が足りなかったか
- 専門家が挙げた事実誤認・根拠不足は、記事の信頼を損なう水準か

## 必要なツール

- ファイルの閲覧：Read
- URL の閲覧：同梱の Playwright MCP（レイアウトと画像込みで体験させるため）
