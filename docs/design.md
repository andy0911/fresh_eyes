# レビュワーAgentシステム：理解の整理と思想の妥当性調査

Nov 3, 2026 · @あんでぃ

## 結論

作るものは「成果物を、著者の文脈を知らない4種のペルソナ・サブエージェントに体験させ、所感・理解度・ギャップ・ネガ・ポジを集めて改善に使う Claude Code プラグイン」です。

思想の妥当性は「条件付きで有効」と判定します。「著者は自分の成果物を初見で見られない」「複数の独立した異視点レビュワーが単独より多く見つける」「意図を隠して生の反応を取る」という核は、認知科学・HCI・ソフトウェア検査の確立した知見と、LLM 評価者バイアスの最新研究の両方で裏付けられます。一方で、LLM ペルソナは実在集団の代表ではなく、用途は「どこで迷うか、何が伝わらないか」の定性的な摩擦発見に限定すべきです。

設計で守るべき3点は次のとおりです。

1. **遮断を徹底する**。目的・意図・前回結果・「改訂版」という情報をペルソナに渡さず、ペルソナ同士も独立させ、照合はシンセサイザーだけが行う。
2. **無垢・素人は「知識状態の仕様」で定義し、逸脱を検知する**。プロンプトだけの「知らないふり」は崩れることが実証されている。
3. **出力は探索的証拠として扱う**。強制順位付けと具体根拠を求め、一致した指摘と分かれた指摘を平均化せずに並べ、割合や優劣の定量的主張はしない。

「設計案」の内容はこのまま有効で、「思想の妥当性調査」末尾の9点を上乗せして構築します。「未決事項」への回答をいただければ、その前提で実装に入ります。

## 要件の理解

一文で言うと「成果物を、著者の文脈を知らない複数ペルソナのサブエージェントに体験させ、所感・理解度・ギャップ・ネガ・ポジを集めて改善に使う Claude Code プラグイン」です。狙いは、著者が自分の成果物を初見の目で評価できない問題を、意図的に無知なレビュワーで補うことにあります。

### レビュワーの4カテゴリ

| カテゴリ | 誰か | 主に見つけるもの | 渡してよい情報 |
| --- | --- | --- | --- |
| 専門家 | 成果物の属性に合う職能（例：デザイン→UXデザイナー、論文→同分野の査読者） | 規範違反、品質の粗、専門的な誤り | 職能名、アクセス手順 |
| 関心がある人 | 題材に興味はあるが非専門の一般読者 | わかりにくさ、魅力の有無、読み続ける動機 | 題材の大まかな分野、アクセス手順 |
| 全く無垢な人 | 題材も文脈も知らない人 | 前提知識なしで何が伝わるか、最初のつまずき | アクセス手順のみ |
| 想定受信者 | 著者が意図した読者・利用者像 | 目的の結果（行動・理解）にどれだけ近づくか | 自分の属性（人物像）、アクセス手順 |

どのペルソナにも「成果物の目的」「著者の意図」「他ペルソナの反応」「過去のレビュー結果」は渡しません。これが本システムの核になる制約です。

### 出力の5項目

| 項目 | 誰が出すか | 補足 |
| --- | --- | --- |
| 1. 純粋な所感 | 各ペルソナ | 体験直後の率直な感想。評価軸を与えない |
| 2. アウトプットに対する理解度 | 各ペルソナ→統合側で採点 | ペルソナは「何だと理解したか」を自分の言葉で述べ、統合側が意図と照合して採点 |
| 3. 目的の結果に対してのギャップ | 統合側 | ペルソナは目的を知らないため、統合側が「目的」と「2.の理解」「次に取る行動」を比較して算出 |
| 4. 属性ごとのネガティブポイント | 各ペルソナ | つまずき、不満、信用できなかった点 |
| 5. 属性ごとのポジティブポイント | 各ペルソナ | 伝わった点、好ましかった点 |

### 対応するアウトプット6種と受け取り方

| 種別 | 受け取る形 | ペルソナの体験手段 |
| --- | --- | --- |
| デザイン | 画像ファイル、PDF、Figma リンク | 画像の閲覧（Read）、Figma MCP（任意） |
| 記事 | Markdown、テキスト、公開URL | ファイル閲覧、WebFetch |
| アプリの挙動 | 起動手順付きのWebアプリURL、CLI、画面録画・スクリーンショット | Playwright MCP、Bash、画像閲覧 |
| Webサイトの動作 | URL | Playwright MCP（操作とスクリーンショット） |
| テキストベースの論文 | PDF、Markdown、LaTeX | ファイル閲覧（PDF は Read が直接読める） |
| 発表用スライド | PPTX、PDF、Keynote書き出しPDF | MarkItDown で Markdown 化、PDF はそのまま閲覧 |

### プラグインとして同梱するもの

- オーケストレータのスキル（`/reviewer-agents:review`）と、種別ごとの準備・アクセス手順スキル6本
- ペルソナのサブエージェント定義4本と統合（シンセサイザー）エージェント1本
- MCP サーバ設定：Playwright MCP（Web・アプリ。同じ体験の再現に必須）のみ。文書変換は同梱スクリプトが MarkItDown を実行。コネクタ系（Figma 等）は同梱しない
- 補助スクリプト：文書の Markdown 変換、ペルソナ向けプロンプトの情報漏れチェック
- レポートの雛形と README

## 設計案

「オーケストレータが成果物を準備し、4ペルソナを独立に並列起動し、回収した生の反応をシンセサイザーが目的と照合して統合レポートにする」3段構成です。目的と受信者像はシンセサイザーにだけ渡し、ペルソナには渡しません。

&#91;embedded content: レビューの流れ · 入力2種、ペルソナ4体、統合1段\]

成果物だけがオーケストレータ経由でペルソナに届き、目的と受信者像は点線のとおりシンセサイザーにだけ届きます。

### 情報遮断のルール

| ペルソナに渡す | ペルソナに渡さない |
| --- | --- |
| 自分の人物像（専門家は職能、想定受信者は属性） | 成果物の目的、著者の意図、期待する行動 |
| 成果物の種別とアクセス手順（パス、URL、起動コマンド） | 他のペルソナの存在と反応、前回のレビュー結果 |
| 制限時間と回答の形式（評価軸は含めない） | プロジェクトの CLAUDE.md、変更履歴、著者が同席していること |

実装上の担保は3つです。ペルソナは fork ではなく白紙のサブエージェントとして起動し、`omitClaudeMd: true` でプロジェクト文脈を読ませません。起動前にスクリプトがプロンプトと目的文の特徴語の重なりを機械的に点検します。ペルソナ同士は別セッションで、互いの出力を見る手段がありません。

### 5項目の算出方法

ペルソナの回答は「所感」「理解したこと（何のためのものか、誰向けか、要点、次に自分が取る行動）」「つまずき・不明点」「ネガティブ」「ポジティブ」「体験ログ（何をどの順で見たか）」の6ブロックです。シンセサイザーはこれに「目的」「想定受信者」「期待する行動」を重ねて、理解度を「核心・対象読者・次の行動」の3点一致で採点し、ギャップをペルソナごとに記述します。

最終レポートは「ペルソナ別の5項目」「横断して現れたパターン」「改善案（P1へP3の優先度付き）」「残すべき強み」「次回確認したい点」の順で、`reviews/` 配下に Markdown で保存します。改善後は同じコマンドをラウンド指定で再実行し、ペルソナには前回を渡さずにシンセサイザーだけが前回との差分を述べます。

### 運用上の選択

- ペルソナのモデルは既定で呼び出し元を継承。コストを下げる場合はペルソナだけ Sonnet、シンセサイザーは上位モデルにする。
- 4ペルソナは1メッセージで同時起動し、ペルソナの追加（例：競合、文化圈が違う読者）はオプションで増やせる。
- 目的と受信者像が指定されていないときは、ペルソナ起動前に一度だけ質問して確定する。

## 思想の妥当性調査

結論は「思想の核は有効だが、用途を定性的な摩擦発見に限定し、LLM固有の3つの弱点に設計で対処すれば成立する」です。根拠は3系統（人間側の認知科学・HCI、LLMペルソナ模擬、マルチエージェントレビューと評価者バイアス）で調べ、文献はすべて一次ソース（arXiv、Crossref、出版社ページ）を取得して書誌を照合しました。

### 有効とされる根拠

| 本システムの前提 | 裏付ける知見 | 主な文献 |
| --- | --- | --- |
| 著者は自分の成果物を初見の目で見られない | 知識の呪いはインセンティブやデバイアス指示でも消えない。話し手は伝達成功率を系統的に過大評価する | Camerer ら 1989、Hinds 1999、Keysar & Henly 2002、Kruger ら 2005 |
| 専門家だけでは足りず、無矢・素人ペルソナが要る | 専門家は初学者の躉きを逆に予測する（専門家の盲点）。専門家評価とユーザーテストで見つかる問題の種類が違う | Nathan & Petrosino 2003、Jeffries ら 1991 |
| レビュワーは複数・独立・異なる視点で | 単独評価者の発見率は2〜5割。評価者に別々の視点を割り当てる方が同一観点より検出率が高く、会議（相互議論）は検出をほぼ増やさない | Nielsen & Molich 1990、Porter ら 1995、Votta 1993 |
| 4ペルソナ程度で意味がある | 独立評価者5名で約85%の問題を発見。ただし最悪ケースは35〜55%まで落ちる | Nielsen & Landauer 1993、Faulkner 2003、Spool & Schroeder 2001 |
| 形式は「生の所感→理解→意図とのギャップ」 | 非専門家クラウドで同構造のフィードバックが実証済み。理解確認は受け手に再述させる（teach-back）のが有効 | Xu ら 2014 (Voyant)、Luther ら 2015 (CrowdCrit)、Schillinger ら 2003 |
| LLM の複数ペルソナレビューは単一より良い | 役割を分けた複数レビュワーは人間評価との一致が高く、同一ペルソナにすると性能が落ちる。観点特化で汎用コメントが半減 | Chan ら 2023 (ChatEval)、D'Arcy ら 2024 (MARG)、Sahu ら 2025 |
| 目的・意図をレビュワーに隠す | RLHF 済みモデルは利用者の見解に迎合する。参照解や「改訂版」という枠組みを見せるだけで評点がアンカーされる | Sharma ら 2023、Kapetanovic ら 2026、Li ら 2025 |
| ペルソナ同士を独立させる | 他者の意見を見せると多数派同調が起き、似たモデル同士の議論は共通の誤解へ収束する | Koo ら 2023、Jin ら 2024 (AgentReview)、Estornell & Liu 2024 |

### 限界と反証

| 限界 | 何が起きるか | 主な文献 |
| --- | --- | --- |
| 無垢の演技が崩れる | 高能力モデルに「知らないふり」をさせても専門知識に戻り、人間なら間違える問いに正解しすぎる（過剰正確性、能力の逆説） | Aher ら 2023、Yuan ら 2026、Song ら 2026 |
| 同質化・戯画化 | 同じペルソナを何度走らせても多様性が出ず、役割っぽい定型句に偏る。属性ペルソナはステレオタイプを再生産する | Park ら 2023、Cheng ら 2023 (CoMPosT)、Wang ら 2024 |
| 集団の代表にはならない | 平均は似ても分散や回帰構造が違う、「何％が好むか」「AとBのどちらが良いか」を推定すると誤った結論に至る | Bisbee ら 2024、Santurkar ら 2023、MeasuringU 2024 |
| 浅く好意的で、全部を気にする | 合成ユーザーは優先順位を付けず、深掘りに曖昧にしか答えない | Nielsen Norman Group 2024、Liang ら 2024 |
| モデル依存で結果が揺れる | 使うモデルによって模擬ユーザーの結論が最大約9ポイント変わる | Seshadri ら 2026 |
| 自己選好は文脈分離だけでは消えない | モデルは文体から自分の出力を識別し、馴染みのある文を好む | Panickssery ら 2024、Wataoka ら 2024、Mahbub & Feng 2025 |
| ペルソナは能力を上げない | システムプロンプトのペルソナは客観タスクの正答率を改善しない。視点の切替手段と割り切る | Zheng ら 2024、Hu & Collier 2024 |
| 多エージェントの利得は「独立サンプルの集約」が本質 | 議論させる方式は強い単一プロンプトを安定して上回らない | Smit ら 2024、Wang ら 2024 |

### 設計への反映

調査を受けて、最初の設計案に次の9点を追加・強化します。

1. **ペルソナは属性ではなく「保有する文脈と知識状態」で定義する**。性別や年齢ではなく「何を知っていて、何を知らず、どう誤解しやすいか」を列挙した仕様を渡す（Yuan ら 2026、Lu & Wang 2024）。
2. **無垢・素人ペルソナには逸脱検知を入れる**。出力に専門用語や自力解決が現れたら逸脱とみなして再試行する（Song ら 2026、Do ら 2026）。
3. **生の所感は理由づけを求めず、見た順に記録させる**。第一印象を熟慮後の判断と別枠にする（Ericsson & Simon 1980、Lindgaard ら 2006）。
4. **理解度は teach-back 形式で取る**。ペルソナに「何のためのものか、誰向けか、要点、次に自分が取る行動」を自分の言葉で再述させる（Schillinger ら 2003）。
5. **ネガ・ポジは「どこで・何が・なぜ」を必須にし、上位3件の強制順位付けを求める**。「全部気にする」「好意的すぎる」を抑える（Krause ら 2017、NN/g 2024）。
6. **専門家には具体的な専門背景と具体的な問いを与える**。抽象的な「批評せよ」より「誤りを特定せよ」が効く（Xu ら 2023、Liu & Shah 2023）。
7. **シンセサイザーは一致した指摘と分かれた指摘を平均化せずに並べ、指摘の妥当性を反論で検証してから優先度を付ける**（Pier ら 2018、Zou ら 2026）。
8. **再レビュー時に「改訂版」という情報や前回スコアをペルソナに渡さない**。レビュワーには著者が生成に使ったのと別のモデルを指定できるオプションを用意する（Kapetanovic ら 2026、Panickssery ら 2024）。
9. **レポートに「探索的・要人間検証」のラベルを付け、割合や優劣の定量的主張を禁じる**。重要な成果物では各ペルソナ2体以上か反復を推奨する（Hullman ら 2026、Faulkner 2003）。

| 論点 | 決定 |
| --- | --- |

| 専門家の職能とレポートの言語 | 種別ごとの既定プロファイルを `--expert` で上書き。言語は日本語既定、`--lang` で変更 |
